# Git Backlog Issue Workflow

## Product-owner perspective

Start from the product or project outcome: who needs it, what problem or
opportunity it addresses, and what coherent slices could belong in the
backlog. Treat the output as product-owner discovery, not an implementation
plan. Do not decide technical design, architecture, or delivery details here.

## Backlog Issues

Create many small draft issue candidates.

Use this for initial product backlog discovery under
`docs/development-workflow.md`. For selected-story children and issue enrichment,
use `git-issue-workflow`; do not run another rough-backlog pass.

Each candidate must include only:

- Title.
- Description.

Do not add type, labels, acceptance checks, edge cases, dependencies, implementation details, or GitHub issue links.

Do not publish to GitHub Issues.

Stop for human review.
